Deployment Guide

One Paytm upstream stream feeding many site users. Scale API replicas horizontally; keep the ingest worker as a singleton unless you intentionally shard subscriptions.

Service architecture

Four containers compose the backend. Only the API process is publicly reachable. All inter-service communication goes through Redis pub/sub.

api

Public edge

HTTP API and user WebSocket gateway. Exposes readiness checks, market REST routes, and realtime quote fanout. This is the only service behind the load balancer.

ports: 3000 (HTTP/WS)
price-ingest

Stream singleton

Owns the upstream Paytm WebSocket connection. Subscribes to instruments via Redis lease keys, publishes raw quotes to Redis pub/sub.

depends_on: redis, paytm session
redis

Backplane

Pub/sub message bus, subscription lease storage, latest quote cache, and candle cache. All services depend on Redis.

ports: 6379 (internal)
catalog-sync

One-shot job

Refreshes the Paytm security-master snapshot. Runs on-demand or as a cron job. Writes the instrument catalog file.

output: data/instruments.snapshot.json
!

Traffic rule

Put the public load balancer in front of api only. Never expose Redis, the ingest worker, or any operator scripts to external traffic. Auth routes must remain 404.

Docker Compose

A Compose file lives at services/api/deploy/docker-compose.yml. It defines all four services with their dependencies and mount points.

Full production start

Build and start every service:

docker compose -f deploy/docker-compose.yml up --build

Run from services/api. The --build flag rebuilds the API image on code changes. Omit it for faster starts when the image is current.

Local dev (Redis only)

Start only Redis:

docker compose -f deploy/docker-compose.yml up redis

Use this when running the API and worker via bun run dev and bun run worker:ingest outside containers.

Compose file structure (reference)

services:
  redis:
    image: redis:7-alpine
    ports: ["6379:6379"]
    volumes: ["redis-data:/data"]

  api:
    build: ..
    ports: ["3000:3000"]
    depends_on: [redis]
    env_file: ../.env
    volumes: [../data:/app/data]

  price-ingest:
    build: ..
    depends_on: [redis]
    env_file: ../.env
    volumes: [../data:/app/data]

  catalog-sync:
    build: ..
    depends_on: [redis]
    env_file: ../.env
    volumes: [../data:/app/data]

Environment configuration

All configuration is passed through environment variables. The .env file at services/api/.env is loaded by Docker Compose and Bun.

VariableRequiredDescription
PAYTM_API_KEYyesPaytm SmartConnect API key.
PAYTM_API_SECRETyesPaytm SmartConnect API secret.
PAYTM_CALLBACK_URLyesOAuth callback URL registered with Paytm.
REDIS_HOSTnoRedis hostname (default: localhost).
REDIS_PORTnoRedis port (default: 6379).
PORTnoAPI server port (default: 3000).

Security note

Keep the .env file out of version control. Add it to .gitignore and use .env.example as the committed template.

Scaling

The system is designed for asymmetric scaling. The ingest side is a singleton; the serving side scales horizontally.

Horizontal

API replicas

Scale api freely behind your load balancer. Each replica connects to the same Redis backplane and serves the same HTTP/WS surface. No per-replica state beyond the Redis connection.

Singleton

Ingest worker

Keep price-ingest at one replica by default. Multiple workers create duplicate upstream subscriptions to Paytm. Shard only if you deliberately split symbol groups across workers.

Data persistence

Mount a volume or bind-mount for the data/ directory to preserve these files across restarts:

  • — paytm-session.json — avoids re-authentication after deploy
  • — instruments.snapshot.json — avoids re-syncing the full catalog

Without persistence, every container restart requires re-login to Paytm and a catalog re-sync.

Readiness gate

The frontend and load balancer should route market commands only after the readiness endpoint confirms all dependencies.

Check command

curl http://localhost:3000/ready

Healthy response (200)

{
  "ready": true,
  "checks": { "redis": true, "subscriptionLeases": true, "paytmSession": true, "catalog": true }
}

Unhealthy response (503)

{
  "ready": false,
  "checks": { "redis": true, "subscriptionLeases": false, "paytmSession": true, "catalog": true }
}

The checks object shows exactly which dependency failed. Use this to diagnose startup issues before routing traffic.

Production checklist

Verify each item before opening traffic to a new deployment.

Y

Y

Scale intentionally

api can scale freely. price-ingest is locked to one replica.

Y

Readiness passes

/ready returns 200 with "ready": true. All four checks pass.

Y

Provider data flows

bun run verify:paytm -- RELIANCE returns live market data from Paytm.

Y

Public surface locked

Auth routes return 404. Only documented endpoints are accessible. Load balancer targets api only.

Private operator tasks

Run these from the server shell. They are intentionally not HTTP routes to protect Paytm credentials and rate limits.

Generate login URL 
bun run paytm:login-url
Exchange request token 
bun run paytm:exchange-token -- <requestToken>
Verify provider data 
bun run verify:paytm -- RELIANCE
Sync catalog 
bun run worker:catalog
